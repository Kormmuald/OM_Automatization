## Результат и разрешённые изменения

Подготовить четыре последовательные feature specifications 001–004 с использованием
`.agents/skills/speckit-specify/SKILL.md` и всех обязательных hooks.
Общую спецификацию использовать как видение проекта. Отдельной feature 005 не будет:

Удаление старых сгенерированных specs 001–003 и их пересборка разрешены этим заданием,
при соблюдении следующей процедуры. Черновики никогда не являются целью удаления.

Разрешены изменения только в четырёх целевых feature-папках из README,
`.specify/feature.json`, обязательных локальных skipped traces и артефактах RUN_DIR.
Не менять AGENTS.md, skills/workflows, constitution/project.yml, черновики,
старые transfer-prompts или production-код. Связность инструкций закрепит роль 02.

## 1. Проверка и восстановимость перед удалением

1. Прочитай источники и project policy из README; зафиксируй git status, текущую
   ветку, существующие файлы features и feature context. Не запускай clean/reset/checkout.
2. Создай run (или используй переданный), source-manifest и начальный inventory.
3. Точные цели удаления, относительно проверенного project root:
   - `specs/001-read-only-catalog-qualification/`;
   - `specs/002-workbook-pair-control/`;
   - `specs/003-compare-read-only-plan/`.
4. Разреши абсолютные пути; проверь, что это именно перечисленные непосредственные
   дочерние каталоги project-root/specs, не symlink/junction/reparse point и не путь
   внутри preparation. Не удалять сам specs или вычисленные glob-цели.
5. Перед удалением скопируй каждый существующий целевой каталог со всем содержимым
   в `RUN_DIR/backups/`, отдельно сохрани feature.json и inventory/hash manifest.
   Проверь совпадение состава и SHA-256 копий с оригиналами, включая untracked files.
   Ошибка backup останавливает удаление.
6. Если вместо ожидаемых spec/checklist обнаружены планы, tasks, implementation evidence
   или неожиданные пользовательские файлы — сохрани inventory и остановись перед удалением:
   исходное задание опиралось на три draft specs. Не уничтожай более позднюю работу.
7. Удали только проверенные старые feature-каталоги штатным PowerShell с LiteralPath.
   При повторном запуске этой роли проверь checkpoints run: не удаляй уже пересобранное.
   Существующую 004 не удалять; если она появилась вне текущего run, остановиться перед
   её перезаписью и запросить решение.
8. В отчёте указать точные удалённые пути, backup и способ восстановления.
   При частичном сбое сохранить новые результаты и backup; не делать скрытый rollback.

## 2. Сохранение требований и распределение OPS

Полностью прочитай общий spec и все пять этапных источников до первого Specify.
Построй source → target матрицу в RUN_DIR/traceability.md:
исходный файл/ID или раздел → целевая feature/requirement → acceptance/check →
статус переноса. Покрыть и не нумерованные требования, риски, ошибки, exclusions,
границы пилота и критерии полной приёмки. Число совпавших IDs не заменяет смысловой сверки.

Включи все READ-001…012, WB-001…013, CMP-001…012, APPLY-001…012, OPS-001…013
и все применимые общие FR/NFR. Сохрани исходные IDs как qualified source references;
новые FR IDs могут отличаться. Слияние и разделение разрешены с трассировкой без потери условий.

Обязательное распределение:
- 001: основной механизм run/audit/evidence и защиты секретов (OPS-001…003);
  базовая настройка/чтение/диагностика skills и ранние части передачи (OPS-012…013).
- 002: применение того же механизма к workbook-командам, идентичности пары, snapshot;
  skills выгрузки/валидации и актуализация операторских шагов.
- 003: применение audit к compare/plan, материал детерминированной выборки OPS-005,
  безопасный report и skills сравнения; контракт результатов для будущего Apply.
- 004: полная browser verification OPS-004…007, Git-сценарий OPS-008…011,
  завершение OPS-012…013, установка/передача на чистой машине и общая приёмка MVP.
  Полный CLI read-back и browser acceptance обязательны до успешного Git.
Для сквозных требований указать одного владельца общего механизма и каждого потребителя.
Не создавать циклическую зависимость 001 от будущей 004 ради audit.
Не откладывать NFR-009 архитектурного разделения только потому, что он сквозной.

Full-catalog reader qualification и качество/масштаб Excel-пары должны остаться
проверяемыми обязанностями 001 и 002 соответственно. Ограниченный baseline — промежуточное
доказательство, а не замена конечных требований. Недопущенные write kinds остаются
DENIED/blocker; разработка/специфицирование безопасных локальных checks и live admission —
разные состояния.

## 3. Реальное выполнение Specify

1. Прочитай Specify, class gate, navigator и применимые hook skills.
2. Последовательно выполни четыре отдельных Specify с явным
   SPECIFY_FEATURE_DIRECTORY, соответствующим каждой точной папке из README.
   Перед каждым вызовом назови общий source, этапный source и source 05 неизменяемыми.
3. Используй активный шаблон, заполненный spec.md и честно проверенный
   checklists/requirements.md. Не ограничивай команду одним файлом.
   Обязательные hooks реально выполняются; disabled sync даёт локальный skip,
   а не внешние изменения и не полное отключение hooks.
4. Каждая spec содержит ссылку на общее видение, связь с предшественниками,
   применимые OPS, новые обязанности, границы, критерии приёмки и будущую регрессию.
   Технические ограничения источников не терять ради шаблона: отделить обязательные
   domain/safety contracts от ещё не принятых проектных решений.
5. Не угадывай решения человека и не помечай checklist выполненным при известном пробеле.
   Вопросы задавай по правилам навыка; при блокировке запиши промежуточный handoff.
6. Будущие plan/test-plan/tasks и memory после Archive не создавать.
   В spec допускаются требования к их будущему содержанию.
7. После всех четырёх Specify установи feature context обратно на 001 для будущего Clarify.
   Зафиксируй, что navigator рекомендовал после каждого вызова, и что ничего дальше
   Specify не было исполнено.
