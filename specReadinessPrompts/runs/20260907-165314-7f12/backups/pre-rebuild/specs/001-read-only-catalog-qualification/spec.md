# Спецификация функции: безопасный read-only контур и qualification каталога BPMSoft

**Ветка функции**: `001-read-only-catalog-qualification`
**Создано**: 2026-09-07
**Статус**: Черновик для `/SpecKit Clarify`
**Класс**: L2 — Pilot (`l2-pilot`)

## Источник и назначение

Неизменяемый исходный материал: `preparation/docs/product-specs/local-bpmsoft-synchronizer/spec.md`. Этот файл и весь каталог `preparation/docs/product-specs/` являются только источником; они не редактируются, не перемещаются и не являются `SPECIFY_FEATURE_DIRECTORY`.

Эта feature — первая самостоятельная, проверяемая ценность пилота: безопасно прочитать каталог локального BPMSoft и квалифицировать обобщённый reader. Она не является спецификацией всего синхронизатора и не разрешает какой-либо write path.

## Границы L2-пилота

### Пользователи, среда и данные

- **Test operator**: владелец на выделенном локальном стенде либо уполномоченный BPMSoft developer в Windows/local BPMSoft/desktop Excel environment — ровно в том объёме, который будет подтверждён при уточнении.
- **Reviewer**: человек, который изучает безопасные результаты qualification и принимает решение по пилоту; skill не принимает это решение.
- **Среда и данные**: реальная локальная среда BPMSoft и рабочие данные её каталога в ограниченных границах L2-пилота. Конкретные стенд, версия, состав каталога, участники и правила работы с данными пока не подтверждены.

### Разрешённый безопасный subset

Разрешён только интерактивный вход, необходимый для чтения, и чтение через явный endpoint allowlist. Конкретный allowlist в источнике не задан, поэтому данная спецификация не устанавливает и не предполагает ни одного endpoint. До его явного определения и проверки выполнение read-run не допускается.

Read-run получает каталог детерминированно, постранично и без изменения BPMSoft, браузера, Excel-книг или иной пользовательской информации. Ценность пилота — наблюдаемая qualification reader либо ограниченный по области blocker; не создание или изменение данных.

### Не входит в эту feature

- Логическая пара Excel-книг, её генерация, валидация и обновление (`FR-006`–`FR-008`) — будущая самостоятельная feature **workbook pair**. Её ограничения по парной целостности, identity, формулам, ссылкам и `Desired*` сохраняются.
- Compare и immutable plan (`FR-009`, `FR-010`, `FR-012`) — будущая самостоятельная feature **compare/immutable plan**. Она должна оставаться read-only и связывать plan с обеими книгами, template/baseline и состоянием цели.
- Write preflight, owner allowlist, ручное подтверждение backup, Apply, server identity after create, read-back и browser verification (`FR-013`–`FR-018`) — будущая feature **gated Apply**. Никакие write semantics, operation kinds, allowlist или доказательства для неё этой feature не определяются.
- Финализация Git (`FR-020`) — будущая feature **Git finalization**. Её условие — только полный успех, явное решение человека и атомарный commit обеих книг; конфликты не разрешаются автоматически.
- Delete, SQL delete, browser write actions, automatic backup/restore, automatic rollback, скрытый bidirectional merge и любое изменение BPMSoft исключены. Отсутствие write path не является поводом предполагать или описывать write semantics.
- Любая реализация, production-код, `plan.md`, `tasks.md`, live BPMSoft write action и прочие артефакты feature, кроме данного `spec.md`.

## Пользовательский сценарий и независимая проверка

### Пользовательская история 1 — квалифицировать безопасное чтение каталога (Приоритет: P1)

Как test operator, я хочу выполнить разрешённый read-only проход по согласованному каталогу реальной локальной среды, чтобы получить воспроизводимое основание для решения: reader квалифицирован в заданной границе либо есть явный ограниченный blocker.

**Почему этот приоритет**: это минимальная самостоятельная ценность, которая проверяет работу с реальной средой, но не меняет её и не открывает сквозной цикл синхронизации.

**Независимая проверка**: после явного определения разрешённой границы оператор запускает контролируемый двойной проход. Проверка сопоставляет требуемые `FR-005` наблюдения обоих проходов: количества, упорядоченные идентификаторы, hashes, пропуски/дубликаты, масштаб и перечень неподдерживаемых элементов. Результат — qualification либо fail-closed blocker; отсутствие или неоднозначность наблюдений не может быть засчитана как успех.

**Сценарии приёмки**:

1. **Дано** утверждённое для пилота описание каталога и endpoint allowlist, **когда** оператор выполняет read-run, **тогда** все обращения остаются в разрешённом read-only контуре, а collection reader применяет явный порядок, pagination и guards.
2. **Дано** два контролируемых read-only прохода одной согласованной границы, **когда** qualification сравнивает обязательные наблюдения, **тогда** она либо фиксирует воспроизводимую qualification, либо выдаёт ограниченный blocker без скрытого пропуска и без изменения целевой среды.
3. **Дано** неизвестная структура, неоднозначная identity, неразрешённый endpoint, признак HTTP write, duplicate/skip, отсутствие termination condition либо риск раскрытия секрета, **когда** это обнаружено, **тогда** run завершает затронутую ветвь fail-closed и передаёт вопрос человеку.

## Требования

### Функциональные требования

- **FR-001 Приоритет источников.** Любое решение этой feature соответствует конституционной иерархии источников; исторический `SyncOM` классифицируется как `reuse/rewrite/drop/defer`, а не переносится молча.
- **FR-002 Список разрешённых операций чтения.** Read-run использует только интерактивный вход и явно разрешённые endpoints чтения; контрактная проверка должна доказать отсутствие HTTP write calls. Конкретный endpoint allowlist остаётся вопросом для уточнения.
- **FR-003 Полный считыватель.** Чтение коллекций использует явный детерминированный порядок, pagination, защиту от дубликатов, пропусков и бесконечного выполнения, а также телеметрию.
- **FR-004 Неизвестные структуры.** Неизвестная структура сохраняется losslessly как перечень неподдерживаемых элементов и создаёт ограниченный по области blocker без догадок или скрытой потери данных.
- **FR-005 Допуск полного каталога.** Один контролируемый двойной проход квалифицирует reader по количеству, упорядоченным идентификаторам, hashes, пропускам/дубликатам, масштабу и перечню неподдерживаемых элементов. Пока граница полного каталога не определена, критерий не считается выполненным.
- **FR-011 Идентичность.** Server `Id`, schema `UId`, column `UId`, lookup registry `Id` и `DraftRowToken` остаются разными, невзаимозаменяемыми типами identity. `Name` и `Code` допустимы только как display/diagnostic hint; они не заменяют доказанную identity или package-layer context.
- **FR-019 Артефакты запуска.** Для допустимого будущего read-run сохраняются безопасные audit/evidence/run-journal сведения и метаданные версий в отдельной date-based versioned folder; предыдущие run не удаляются. Формат, состав и правила обращения с такими сведениями не считаются уже доказанными.
- **FR-021 Граница навыков.** Skills могут только оркестрировать CLI и объяснять безопасную диагностику; секреты, credentials и человеческие одобрения им не делегируются.
- **FR-022 Граница индексов.** `Indexes` читаются только как evidence из `schema.indexes[]`; при `INDEX_SYNC_UNRESOLVED` никакой index operation не может быть предложен, запланирован или выполнен.

### Нефункциональные требования

- **NFR-001 Безопасность.** Credentials и данные сессии не сохраняются; для каждого типа будущего run требуется scanning маркеров/секретов. Пароли, cookies, CSRF, login response и Git credentials не попадают в skills, arguments, logs, evidence, Git или этот документ.
- **NFR-002 Детерминированность.** Канонический порядок, сериализация и hashing не зависят от порядка перечисления входных данных или состояния сортировки Excel.
- **NFR-003 Безопасное завершение при ошибке.** Недопустимое, устаревшее, неоднозначное или неподдерживаемое состояние не маскируется как отсутствие действий или успех; затронутая ветвь завершается fail-closed.
- **NFR-004 Сохранность данных.** Неподдерживаемые metadata не пропускаются без перечня и причины.
- **NFR-005 Идемпотентность.** Повторение read-only qualification на неизменной согласованной границе не создаёт данных и должно давать сопоставимый результат; расхождение — сигнал для blocker или человеческого решения, а не скрытой коррекции.
- **NFR-006 Аудит.** Каждое наблюдение и решение qualification трассируется к стабильному ключу и доступным безопасным доказательствам; никаких доказательств заранее не предполагается существующими.
- **NFR-008 Удобство использования.** Guided CLI сообщает безопасную причину остановки, доступный способ устранения и следующее разрешённое действие, не предлагая обход safety gate.

### Ключевые сущности

- **Граница каталога**: явно определённая часть локального BPMSoft, в пределах которой разрешается и оценивается read-only qualification.
- **Read-run**: контролируемое, не изменяющее состояние чтение каталога с наблюдениями для qualification.
- **Unsupported diagnostic**: lossless описание неизвестной структуры и причины ограниченного blocker.
- **Identity**: типизированные идентификаторы BPMSoft, которые не смешиваются и не подменяются `Name`/`Code`.

## Критерии успеха, остановки, fallback и решение человека

### Критерии успеха

Пилот может быть представлен человеку как успешный только если в согласованной границе одновременно выполнено следующее:

1. Read-run не совершил write action в BPMSoft, браузере, Excel-книгах или Git.
2. Контролируемый двойной проход дал все наблюдения из `FR-005` и не выявил неразрешённых endpoint, duplicate/skip, termination failure, неразрешённой identity-подмены или необработанной неизвестной структуры.
3. Все требуемые контрактные и fail-closed проверки были определены и пройдены; отсутствие требования, проверки или наблюдения не заменяется предположением об успехе.
4. В доступных артефактах pilot run отсутствуют secrets и session data.

Точные состав каталога, пороги масштаба, метод фиксации доказательств и критерий сопоставимости hashes требуют `/SpecKit Clarify`; эта спецификация не объявляет их уже принятыми.

### Критерии остановки и fallback

Run останавливается fail-closed при любом неразрешённом endpoint или признаке write, отсутствующем/неполном allowlist, неясной границе каталога, ошибке authentication/network, duplicate/skip, отсутствии termination condition, неизвестной структуре, неоднозначной identity, риске раскрытия secrets или `INDEX_SYNC_UNRESOLVED` для index operation.

Fallback — прекратить затронутый read-run без изменения BPMSoft, браузера, Excel-книг или Git, не выполнять автоматический rollback и передать безопасную диагностику человеку. Эта feature не предписывает восстановление, повтор с расширенными разрешениями или скрытую коррекцию.

### Решение человека после пилота

Reviewer принимает явное решение: признать qualification в подтверждённой границе, запросить изменение/дополнительное уточнение, остановить пилот либо начать следующую самостоятельную feature. Решение не является разрешением на workbook pair, plan, Apply или Git finalization. Регулярное использование, support, monitoring или change management потребуют отдельного рассмотрения повышения до L3.

## Вопросы для `/SpecKit Clarify`

1. Каковы точные локальный BPMSoft стенд, версия, участники и реальная граница каталога для L2-пилота; относится ли `FR-005` к полному каталогу этой среды или необходима заранее утверждённая ограниченная граница qualification?

3. Какие именно наблюдения, критерии сопоставления двойного прохода и порог масштаба подтверждают qualification, а какие образуют blocker?

6. Подтверждается ли, что `INDEX_SYNC_UNRESOLVED` остаётся открытым и что indexes в этой feature имеют только read-only evidence значение?
